# Proposed shared contracts v0.2

The attached four-person build plan is the baseline. These exact payload shapes
are **proposed**, not yet confirmed by Persons 1, 3 and 4. Python source is
`api/schemas.py`; runtime integration is `api/integrations.py`. Regenerate with
`python -m scripts.export_contracts`. Fixture credentials/URLs are examples only.

## Common rules

UUID identifiers; UTC ISO timestamps; latitude/longitude in decimal degrees;
service/travel/shift values in **minutes**. Equipment:
`gloves`, `trash_bags`, `broom`, `shovel`, `wheelbarrow`, `pickup_truck`.
Report states: `received`, `needs_info`, `needs_review`, `linked_to_job`.
Job states: `unassigned`, `assigned`, `in_progress`, `blocked`, `completed`,
`recheck_requested`. `held` and `locked` are separate organizer controls.
Resident `display_status` derives from the linked job or report state.

Staff requests use `Authorization: Bearer <Supabase user JWT>`. Resident
requests use `Authorization: Bearer <report token>`. Organizer/crew roles come
from protected records, never frontend input. Person 4 uses `X-Integration-Key`.
Person 3 optional context reads use the separate `X-Agent-Key`.

`command_id` is a fresh UUID for a logical state-changing command; reuse it only
for an identical retry. `expected_version` is the current resource version.
A replay returns current state without reapplying; a changed payload or stale
version returns 409. Clarification uses **report.version**; recheck and crew/job
updates use the version of their respective resource. The worker replaces
agent-proposed command UUIDs with stable task-derived UUIDs.

Errors use `{"detail":"message"}`. Validation errors are 422 with a `detail`
array of `loc`, `type`, `msg`, excluding rejected input. 401 means missing/invalid
credentials; 403 means disallowed role; 404 also hides resources belonging to
another crew/resident; 409 means conflict; 413/415 reject photos; 503 means an
unavailable dependency. Fetch fresh state after 409; do not create a new command
ID merely to bypass a conflict.

## Frontend endpoints

| Method/path | Access | Request/result |
| --- | --- | --- |
| `GET /health`, `GET /ready` | Public | Liveness / configured DB readiness |
| `GET /auth/me` | Staff | User ID, role, crew ID |
| `POST /reports` | Public | Multipart photo, optional coordinate pair, landmark, note; 201 report + access token |
| `GET /reports/{id}` | Resident token, organizer, assigned crew | Public `ReportView` without credentials or internal triage |
| `GET /reports/by-reference/{reference}` | Resident token, organizer, assigned crew | Same public `ReportView`; reference is trimmed/uppercased and is not a credential |
| `GET /reports/{id}/updates` | Resident token, organizer, assigned crew | `{items, limit, offset, total}`; oldest first; limit 1–100 (default 50), offset ≥0 |
| `GET /reports/{id}/messages` | Resident token or organizer; never crew | Same page envelope; oldest first across the report's linked conversations; transport identifiers excluded |
| `GET /organizer/reports` | Organizer | Paginated `OrganizerReportView` array (`limit` 1–100, `offset`) |
| `GET /organizer/reports/{id}` | Organizer | `OrganizerReportView` plus audit details/decisions |
| `POST /organizer/reports/{id}/decision` | Organizer | `TriageRecommendation` input; audited override returns `OrganizerReportView` |
| `POST /reports/{id}/followup-link` | Resident token | Ten-minute one-time code; Person 4 builds the actual channel link |
| `GET /photos/{id}/access` | Authorized report/job reader | Signed private URL, expires in 300 seconds |
| `GET /jobs` | Staff | Organizer jobs or own crew's jobs, ordered by crew/stop position; MVP cap 100 |
| `GET /jobs/{id}` | Organizer/assigned crew | Job, photo IDs, audit events including completion/recheck reasons |
| `PATCH /jobs/{id}` | Organizer/assigned crew | `JobPatch`; see transition rules below |
| `POST /jobs/{id}/completion` | Assigned crew | Multipart after-photo, command_id, expected_version, optional note |
| `GET /crews`, `PATCH /crews/{id}` | Organizer | Crew state; versioned availability/equipment/shift/start-location edits |
| `GET /plans/current` | Organizer | Current plan or null, with stale flag and estimate label |
| `POST /plans/generate` | Organizer | `{command_id}` → 202 `TaskView` |
| `GET /tasks`, `GET /tasks/{id}` | Organizer | Durable integration status/errors |
| `POST /tasks/{id}/retry` | Organizer | Retry a failed task |

Photo uploads are JPEG/PNG/WebP, at most 8 MiB and 25 megapixels. The server
validates bytes and MIME. Storage keys are generated by the backend; clients
cannot submit arbitrary object paths or URLs. Coordinates may both be absent
for clarification, but a job cannot be created without actionable location.

Creation also accepts `title` (1–160 characters) and `address` (1–500), independent
of coordinates. Supplied values are trimmed and must not be blank. Older callers
may omit them: new reports use `Cleanup report` and a null address. Migration
backfills existing titles as `Legacy report` and leaves unknown addresses null.
Every report has an immutable `public_reference`, `WG-` plus 12 uppercase hex
characters, with database uniqueness. Creation retries retain the same reference;
changing title/address on a retry returns 409. All report views include these
fields. The dashboard maps `public_reference` to its existing `reference` field.
`ReportCreated` and both `/reports` lookup routes use the public `ReportView` and
never include the internal `triage` recommendation. Only organizer-specific
report routes include `triage` in `OrganizerReportView`. Trusted Person 3
snapshots retain it for contextual reasoning.

Identity increment examples: `fixtures/report-created.json` for POST `/reports`,
`fixtures/report.json` for either lookup route, `fixtures/organizer-report-list.json`
for listing, `fixtures/organizer-report-detail.json` for organizer detail, and
`fixtures/auth-me.json` for the Supabase-authenticated role response. Local base
URL is `http://localhost:8000` after setup/startup; no shared dev URL is provisioned.

Report views also expose `updated_at`, `latest_update` (nullable for a legacy
report without events) and `dashboard_status`. `updated_at` is the last customer
update time, falling back to creation time. Messaging-only events do not advance
it. `/updates` projects known report/job events to fixed, safe messages and
excludes internal audit details. Each new update records `report_state` and/or
`job_status` as observed at that time; historical events without snapshots retain
null statuses. Do not substitute today's status for a missing historical value.
`fixtures/report-updates.json` shows the page envelope. Ordering is ascending
`created_at`, then UUID; request subsequent pages by advancing offset.

Map `dashboard_status`/update `status` to the dashboard's existing labels:
assigned, in_progress and blocked → `in-progress`; completed → `resolved`;
all other known states → `submitted`. Preserve the detailed `display_status`,
`state` and update snapshots for missing-info, review and recheck explanations.
The mapping is presentation only and does not change allowed transitions.
Write history by invoking the existing validated actions; there is no arbitrary
status/history editing endpoint. Completion messages explicitly mean
crew-submitted evidence, not independent verification.

For retry-safe creation, generate and securely retain a UUID and 32 random bytes
before submitting. Send the UUID as multipart `client_report_id` and the token as
`X-Report-Token: wg_r_<43-character base64url random value>`. Identical retries
return the same report/token. Changed content returns 409. Legacy creation
without both fields generates credentials once; losing that response has no
token recovery mechanism. Never log or put these values in a URL.

Crew transitions: assigned → in_progress/blocked; in_progress → blocked;
blocked → in_progress only with a valid current assignment. Completion is a
separate evidence endpoint. Organizer changes require `reason`; they can hold,
release, reassign, lock/unlock, and resolve blocked/recheck jobs back to
unassigned. Completed/ongoing work cannot be reassigned or held. Reassignment
locks the chosen crew and queues plan validation; a fresh validated plan is
required before starting. Held work stays unassigned.
Blocking an assigned job makes the current plan stale. The planner must retain
that crew and stop in its next validated plan; the crew may resume only after
that plan exists and availability, equipment, and shift capacity still pass.
An unassigned blocked job remains unassigned until organizer intervention.

Crew edits release unlocked assigned jobs, preserve completed/ongoing/locked
work, mark plans stale and enqueue replanning. If a locked job's resources become
ineligible, the worker rejects an infeasible plan; the organizer must unlock or
reassign it. The backend does not silently violate the lock or permit a new start.

## Person 3 boundary

With Chalk configured, the worker defaults to `api.decisions.AssessmentDecisionProvider`.
It implements the following methods over validated snapshots without extra model
calls. An explicitly configured Python factory or HTTP facade takes precedence:

| Python method | HTTP POST | Typed input → output |
| --- | --- | --- |
| `triage_report` | `/triage` | `TriageInput` → `TriageRecommendation` |
| `generate_plan` | `/plan` | `PlanningInput` → `PlanProposal` |
| `handle_followup` | `/followup` | `FollowupInput` → `FollowupResult` |

The worker owns calls/retries. Providers return recommendations and do not write
the database. The facade receives bearer `PERSON3_API_KEY` if configured.
Triage input includes a short-lived photo URL, report/job snapshot, equipment
catalog and up to 20 nearby open reports within 1 km (from the latest 200 reports).
This is bounded MVP context, not an exhaustive geospatial index. Optional tools:
`GET /internal/agent/reports/{id}/snapshot` and `/nearby`, with `X-Agent-Key`.
Resident tokens and link codes are excluded from every reasoning payload.

Backend triage rules are explicit: hazards → review; missing location/details →
needs_info; insufficient evidence → review; uncertain duplicates → review.
`duplicate_candidate_id` refers to another **report**. Confirmed linking requires
that report in `evidence_report_ids` and an open linked job. Ordinary creation
requires location, sufficient evidence, equipment, and a positive service estimate.
An organizer-only decision can approve a settled assessment for job creation or
linking, clearing the review flag with an actor/reason/previous-state audit. Raw
assessment output is preserved. An explicit organizer review is persisted independently of the assessment;
automatic completion/triage and clarification cannot clear it. A successful audited
organizer approval clears the hold. Coordinate clarification runs the same configured
proximity review as submission and excludes the report itself. Pending assessments cannot be overridden, and
automated decisions cannot grant themselves this exception. Nearby real reports
are retained with private possible-duplicate evidence, never automatically merged.
The backend stores the recommendation and applied state; confidence alone has no
approval meaning. All report originals remain separate. Clarifications append
history; they do not replace the original note.

Planning input `node_ids` defines both matrix axes: crew depots then unfinished
jobs, each sorted by UUID. Values are minutes; use the exact supplied label.
`completed_minutes` reserves already consumed shift time. `fixed_assignments`
contains in-progress, assigned-blocked, and manually locked stops that must
retain crew, position and service duration. Preserve already consumed travel
for in-progress work; blocked and pending locked stops may receive updated
travel estimates for the validated route.
Preserve completed work outside the unfinished-job output. Each unfinished
job appears exactly once in assignments or unassigned, with a supported reason.
The backend checks resources, positions, unchanged service estimates, travel
lower bounds, shift budgets, fixed assignments and revision freshness. A stale
revision is retried from current state. Estimates use straight-line distance ×
1.3 at 20 km/h, clearly labeled; Person 3 must coordinate any matrix changes.

Follow-up input includes linked conversation identity, incoming text and current
snapshot. Allowed actions are `none`, `clarification`, `recheck`. State is checked
again after reasoning. A rejected action never sends a success reply. Replies
are placed in the same durable outgoing store as status events.

## Person 4 boundary

1. Resident obtains a link code. Person 4 owns channel opt-in/link UX.
2. `POST /internal/conversations/bind` with code, channel, external_id and
   `opted_in:true` returns the persistent internal conversation UUID. For iMessage,
   external_id is the Photon `space_id`. One external conversation maps to one
   report in this MVP; conflicting rebinds return 409.
3. After restart, `POST /internal/conversations/resolve` with channel/external_id
   recovers that UUID. `GET /internal/conversations/{id}/snapshot` gets current state.
4. `POST /internal/conversations/{id}/followup` with stable provider `message_id`
   and `text` queues contextual reasoning, returning 202. Identical resubmissions
   return the same task. Person 4 still owns inbound deduplication.
5. If Person 4 invokes the agreed handler separately, its allowed proposal can
   instead go to `/clarification` or `/recheck` under that conversation. These
   routes validate resource versions and allowed transitions. Do not call both
   paths for the same message.
6. `POST /internal/outgoing-messages/claim` with `{limit:20}` returns destination,
   payload, stable message/event IDs and a two-minute delivery lease.
   Generic event payloads contain kind/report_id; fetch the current snapshot to
   compose grounded status. A follow-up reply additionally contains reply_text.
7. Send through Photon, using the outgoing UUID as provider idempotency key where
   supported. Then POST `/{message_id}/delivered` with `lease_id`, required
   `sent_text` (the exact text sent, 1–4000 characters, not blank), and optional
   `provider_message_id`. The full path starts `/internal/outgoing-messages`.
   On failure POST
   `/{message_id}/failed` with lease_id and retry_after_seconds. Expired claims
   become claimable after a crash. Old lease acknowledgements return 409.

Delivery is at-least-once: if sending succeeds but acknowledgement is lost,
provider-side deduplication is needed to avoid a repeated message. State changes
are independently idempotent. The backend never contacts Photon itself.

Inbound `/followup` acceptance saves message history and the reasoning task in
one transaction. The same conversation/provider message ID and text returns the
same task; changed text conflicts. Blank incoming text is rejected. Successful
delivery acknowledgement saves the actual sent text and delivery state in one
transaction, deduplicated by outgoing UUID. Repeating it with different text or
provider ID returns 409. Retries must repeat the original payload. The optional
provider ID is omitted when Photon does not return one; do not invent it.

History records expose only backend message UUID, `created_at`, `direction` and
`body`. Inbound time means server acceptance; outbound time means successful-send
acknowledgement, not an independently verified recipient-read timestamp. Queued,
failed and unacknowledged messages are excluded from outbound history. History
starts when this migration is deployed; earlier task/outbox content is preserved
but not reconstructed as a reliable transcript. No history edit endpoint exists;
the explicit demo reset can remove illustrative messages with their demo dataset.

The new Photon SQLite ledger on upstream main remains transport-owned. Persist
our outgoing UUID alongside its provider routing, acknowledge our delivery only
after send success, and use the existing conversation resolver after restart.
Do not independently generate a second reply through the smoke policy. Full
examples: `incoming-followup.json`, `followup-task.json`, `conversation.json`,
`conversation-snapshot.json`, `outgoing-message.json`, `delivery-ack.json`,
`delivery-status.json`, and `report-messages.json` under `fixtures/`.

Version 0.2 adds report fields and history routes and requires `sent_text` on
delivery acknowledgements. Delivery failures still require only a lease plus
retry delay. Person 3 should regenerate shared models for the expanded report
snapshot; its three provider methods and allowed actions remain unchanged.
